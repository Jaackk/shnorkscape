# P0 audit: `CoresManager.getServiceProvider()` call sites on the native 947 tick wheel

Written September 6, 2026 for pillar P0 of `MIGRATION-BACKLOG.md`. Source of the list: `grep -rn "CoresManager.getServiceProvider()"` over `core/ content/ game/ npc/ api/` of `Ataraxia947/` = **337 lines in 170 files** (core 6, content 174, game 68, npc 77, api 12), matching the count in the backlog. Four of the 337 are comments or javadoc (`CoresManager.java:97`, `AraxxorEnvironment.java:400`, `AraxxorInterfaces.java:122`, `ServerLauncher.java:348`); they are kept in the table so the total reconciles.

## What changed (P0)

| | |
|---|---|
| Problem | `CoresManager.init()` constructs and starts `WorldThread` plus the fast/slow pools before assigning `serviceProvider` (`core/com/rs/cores/CoresManager.java`, `init()`); `Native947World` forbids `WorldThread` in its JVM, so `getServiceProvider()` was null and every site below would NPE. |
| Fix | `core/com/rs/cores/Native947TickScheduler.java`: a tick wheel with the same public surface as `ServiceProvider`, drained on the calling world thread. `CoresManager.initNative947(scheduler)` installs `ServiceProvider.Native947ServiceProvider` (a nested subclass that overrides every non-final method to delegate to the wheel) WITHOUT constructing `WorldThread` or the pools. `CoresManager.drainNativeTick()` drains it. `CoresManager.init()` is unchanged for 910 apart from a guard that throws if the native scheduler is installed. |
| Tick | `Native947World.pumpSchedulers()` runs at the top of every 600 ms tick, before `session.tick()`: `WorldThread.WORLD_CYCLE++` (content reads it next to `World.currentTime`), `CoresManager.drainNativeTick()` (game-task queue, then due wheel entries), `WorldTasksManager.processTasks()`. This is the head of `WorldThread.run()` (`WorldThread.java:26-32`). It runs even with no session attached. |
| Time | Wall-clock delays/periods -> `ceil(ms / 600)` ticks, minimum 1. `executeNow` runs at the next drain. Tick-based overloads are used as-is (min 1). |
| Failure policy | An `Exception` in a task is caught, logged (`Logger.getGlobal().error`) and counted (`failed()`); one-shot tasks are done, repeating tasks keep their schedule (legacy parity: the 910 wrappers catch `Exception` around `r.run()`). An `Error` is caught too (the world tick survives) but the entry is removed, which is what the legacy executor effectively did. Nothing is retried silently. |
| Threads | Submissions may come from any thread; the first `tick()` binds the owner thread and any other thread that ticks throws. `Future.get()` on the owner thread runs the pending one-shot inline and counts it (`inlineGets()`), because blocking would deadlock the only world thread; the count tells you which drop-classified caller is still alive. |
| Tests | `tests/modern947/Native947TickSchedulerTest.java` (14 tests): tick rounding, `executeWithDelay` after `ceil(delay/600)` drains, delay measured from the submitting tick, repeating task every N ticks + cancel via `scheduleRepeatingTask2` future, `FixedLengthRunnable.repeat()==false` and `stopNow` leave the wheel, exceptions counted and wheel continues, `Error` removes the entry, game-task order, tracked tasks and duplicate keys, callables/consumers on the draining thread, inline `get()`, foreign-thread `tick()` rejected, `WorldTasksManager.schedule(task, 2)` fires on the third drain of the fake loop, `initNative947` installs a provider whose every non-final `ServiceProvider` method is overridden (reflection) and never constructs `WorldThread`. `Native947WorldLifecycleTest` still passes with the pump in place. |

## Classification used in the table

* **tick-safe** - ordinary game logic that wanted a delay or a period. On the wheel it runs on the world thread at tick granularity. Nothing to change; sub-second periods now mean "once per tick".
* **must-run-on-world-thread** - the 910 code mutated entities, regions or `MapBuilder` from a pool thread (an existing race the legacy server tolerated). On the wheel these run on the world thread, which is the correct place; they are listed separately because their timing observably changes (see below) and because they are the sites that would have raced with the native transport/NPC view thread checks.
* **drop / stub** - external integration that must not run in the single-player 947 dev world: SQL (GIM, hiscores, votes), Java-serialized account saving, Discord, file logging, GE price recalculation, backups, poll/lottery file databases. They are not edited in P0 (no call sites were touched); they simply never get reached because their initialisers are not run natively, or, if reached, they run once on the world thread and are visible in the scheduler counters. A follow-up may stub them behind `CoresManager.isNative947()`.
* **mixed** - files whose sites fall in more than one class; the reason column lists each line.
* **n/a** - comment/javadoc, or code that is unreachable in the native JVM (`Region.checkLoadMap` returns via `loadModernMap()` when `Cache.isFlatReadOnly()`; `WorldThread` is never constructed).

Totals: tick-safe 194 sites / 102 files; must-run-on-world-thread 37 / 16; drop 97 / 47; mixed 5 / 2; n/a 4 / 3.

## Behavioural differences worth knowing before M2b

1. **Sub-tick periods are coarsened.** `Entity.setNextForceMovement` (`Entity.java:1152`, 1 ms poll), `Player.vecnaTimer` (`Player.java:6160`, 1 ms period), `LightPathMechanic` (600 ms) and the many `scheduleFixedLengthTask(..., 1, 1)` second-based timers now run every 1 or 2 ticks. Force movement still applies each tile at the first tick boundary at/after its millisecond deadline (correct: the tile can only be sent at a tick anyway). The vecna countdown changes meaning (per tick instead of per ms) and must be re-checked when that item is enabled.
2. **1 second is 2 ticks.** `toTicks(1, SECONDS) = ceil(1000/600) = 2`. Timers written as "every second" fire every 1.2 s. That is the rounding rule the backlog asked for (round up, never early); if a content path needs exactly one tick it should use the tick overload `executeWithDelay(r, ticks)` or `WorldTasksManager`.
3. **Map building now blocks the tick.** `MapBuilder.copyAllPlanesMap`/`destroyMap` in `MapInstance`, `Cutscene`, `DominionTower`, `FightCaves`, `FightKiln`, `NomadsRequiem`, `QueenBlackDragonController`, `House`, `Dungeoneering`, `DungeonManager`, `PestControl`, `RiseOfTheSixMap`, `AraxxorEnvironment` used to run on a pool thread while the world kept ticking. On the wheel they run inside the tick. For the single-player dev world that is acceptable and removes the race; a large dungeon generation will stall one tick.
4. **`World.executeAfterLoadRegion` (`World.java:976`)** polls `isRegionLoaded` once per tick now; with the flat read-only cache regions load synchronously, so the event runs on the first drain after `startTime`.
5. **`NPC.setRespawnTask` (`NPC.java:2765`)** respawns after `ceil(respawnDelay/600)` ticks on the world thread. Respawn timing was already millisecond-based; nothing observable changes apart from the thread.
6. **`Player.finish` retry (`Player.java:2124`)** re-enters `finish()` from the world thread after ~17 ticks instead of from a pool thread; that is safer for the native logout path.
7. **Blocking `Future.get()`** (GIM SQL commands, `GIMBank`, `GIMHighscores`) is a drop class; if any of them is reached natively the scheduler logs a WARN and increments `inlineGets()`.
8. **`ServerLauncher` tasks are not started natively** (account saving, GE recalc, clean memory). `World.init` (`World.java:339`, `addRefreshTargetBuffsTask`) and the activity initialisers it calls are the tasks that WILL land on the wheel the moment P4 calls `World.init`; they are tick-safe but most of them send packets and therefore need the P1 facade first.
